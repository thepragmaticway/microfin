# Develop Microfin

Use Node.js 24 LTS, npm, and Docker Desktop (Linux containers). The application uses Next.js App Router, React 19, HeroUI v3 and Tailwind v4. Dependency versions and the complete dependency tree are pinned in package.json/package-lock.json.

1. Run `npm ci`.
2. Copy `.env.example` to `.env.local`. Set `SUPABASE_PROJ_URL` and `SUPABASE_PUB_KEY` to a **development** Supabase project. They stay server-side; the browser uses authenticated same-origin API routes. Do not use a service-role key.
3. Set `SUPABASE_CONNECTION_STRING` to the project's Session pooler connection string for the migration CLI. URL-encode the password. For a private certificate chain, set `SUPABASE_CA_CERT_PATH` to the trusted root certificate file. TLS verification stays enabled.
4. Inspect the target database and run `npm run db:migrate`. The CLI records checksums in a private migration schema and applies pending migrations together in a transaction. It never resets the database. Do not edit an already-applied migration; add another version instead.
5. Configure Supabase Auth's Site URL and allowed redirects, following [RELEASE.md](RELEASE.md). Start `npm run dev`, then visit `http://localhost:3000`.

The initial app profile is created lazily during workspace creation, using the verified Auth user's UUID. `public.users` holds only the UUID, display name, and creation timestamp. Email and password/session state remain in Supabase Auth. Each workspace has one owner and its own currency/timezone.

The UI uses `/api/...` for all financial requests. Route handlers constrain JSON and verify request origin, services validate input and verified Auth identity, and the DAL calls owner-checked PostgreSQL commands with the caller's JWT. RLS also protects direct reads; ordinary callers cannot write financial tables directly. `read_snapshot` returns a single consistent financial snapshot with exact numeric strings. No ordinary application request uses the database connection string.

## Checks

- `npm run lint` checks source and imports between architectural layers.
- `npm run typecheck` checks TypeScript.
- `npm run test:unit` checks decimal rules, guided actions, report reconciliation, and the payroll-excluded accounting fixture.
- `npm run test:db` creates a disposable PostgreSQL container and tests migrations, RLS/grants, command integrity, concurrency and reversals. Auth identity is emulated only at this SQL-specific layer.
- `npm run test:api` creates disposable PostgreSQL, **real GoTrue Auth**, and PostgREST containers, starts the real Next.js app, and exercises registration, public recovery initiation, cookies, API/service/DAL/RPC integration, tenant isolation and input/origin defenses. A temporary SMTP capture sink observes the actual recovery recipient and delivered link, which the test follows through the application's PKCE callback and password reset.
- `npx playwright install chromium` installs the browser once. `npm run test:e2e` creates the same isolated stack and checks business and personal journeys, invoices/partial collection, reports, workspace switching, keyboard/modal behavior, error state, themes, and responsive layout. Four viewport/theme screenshots are written to `test-results/visual/`.
- `npm run build` creates the production bundle.

The database/API/browser harnesses override Auth/API configuration with disposable local services and never connect to the development/production database. Every run owns a uniquely named Docker network and containers, and removes them in cleanup. A forced process termination may need manual removal of **only that run's** `microfin-test-<id>-*` containers/network. Other running Supabase projects must be left alone. Run these gates sequentially because API/browser runs both build Next.js development output. Test Auth automatically confirms signup email; password recovery goes through the public application action and GoTrue's real SMTP delivery to the local capture sink. The sink accepts test messages only into memory and closes after the run. External email-provider delivery and hosted redirect configuration remain separate release checks.

`npm run db:types` regenerates `src/lib/database.generated.ts` from versioned schema declarations, representing database numeric values as wire strings. Application contracts further narrow kinds, currencies and roles. When changing schema, update the migration, regenerate types, and update the relevant behavioral tests.

## First use

Create a business workspace with THB as home currency, then bank accounts for THB/SGD and MMK cash/wallet as needed. Add software-services income, rent/living-cost expense categories, equipment/deposit assets, owner equity, and per-currency customer/supplier unpaid accounts. Add opening balances through an opening-balance entry, rather than editing account balances. Create a separate personal workspace for Thailand/Myanmar spending.

Use Receive/Spend/Move money and the other guided actions. Foreign rates mean **home currency per one native unit**. A transfer allows different source/destination amounts. Split categories when one payment covers several purposes. Foreign asset/liability discharges retain weighted carried book value and put any difference into the explicitly chosen FX/rounding category. Drafts do not affect reports. Recorded entries are immutable; reverse an error, then record a separate replacement. Reverse dependent payments before reversing an invoice/bill.

Documents/imports/matching, bank connections, revaluation, payroll workflows, budgets and tax filing are deferred. Reports use historical book values, without depreciation or automated closing. The original accounting example's payroll entries are educational; implemented fixture assertions use T01–T07 and T10 only.

From **Accounts**, choose **Open ledger** on a money account or select a category's name to view its ledger. Choose a date range to see the opening balance, period debit/credit totals, chronological journal lines, running balances, and closing balance. The ledger includes posted entries and their reversals, and excludes drafts. Balances use explicit **Dr/Cr** labels. Home-currency values retain historical rates; fixed foreign-currency accounts also show native balances, while any-currency accounts show original line amounts without combining different native currencies. Select an entry to inspect it, or use **Edit account** to change the account's details.

In **Activity**, search descriptions or filter by account, status, and dates. The summary above the results shows the matching count, recorded total, and separate draft total. Totals sum the signed amounts displayed in the matching rows and include matching reversals. A selected account uses debit-positive, credit-negative movement and also shows native totals when its fixed currency differs from the home currency. Across all accounts, transfers between money accounts can net to zero; these search totals are not profit or an account's closing balance.

Use **Activity view** to switch between **Transactions**, **Profit & loss**, and **Balance sheet**. Accounting views use the same posted historical values as **Reports**, with a From–Through period for profit and loss and a single As-of date for the balance sheet. Complete report totals remain visible while description and account filters show a separately labeled **Matching subtotal**. Expand an account to see its matching journal lines, debit/credit totals, report-signed net, original foreign amounts, and links to entry details. Income, liabilities and equity use credit-positive signs. The balance sheet includes all earlier postings and accumulated results once; its income and expense detail contributes to accumulated results in equity. Draft status applies only in Transactions and never affects accounting views.

In either Balance sheet view, select the **Accumulated unclosed profit/loss** amount to open its supporting **Activity → Profit & loss** detail. This starts with all posted history through the selected As-of date, clears account/search filters and excludes drafts. The net result reconciles to the clicked equity component; existing closing journals reduce the unclosed result without adding equity twice. Detail dates are separate from the saved Reports period, and **Back to Reports** restores that context. Opening detail creates no journals or closing entries.

In **Reports**, switch from **Detailed** to **Graphical**, then choose **Profit & loss** or **Balance sheet**. Profit & loss compares period revenue, expenses and net profit/loss, with a monthly trend and ranked revenue/expense accounts. Long periods use labeled annual or multi-year buckets, clipped to the selected dates. Balance sheet compares cumulative assets with liabilities plus equity, shows accumulated unclosed results once, and plots the last twelve monthly closing balances through the As-of date. Negative balances extend below or left of zero. Both presentations reuse the same posted historical home-currency calculations, including reversals and excluding drafts; they do not revalue balances or create closing journals.

Select a total, chart point or category to inspect its supporting **Activity** report group or account. Profit & loss points use their bucket dates; Balance sheet points use their closing As-of date. Equity detail includes equity accounts and the income/expense lines contributing to unclosed results. Drill-down clears stale search/account filters and preserves the Reports dates, chart selection and category choice when returning. Every chart has a keyboard-operable exact-value table alternative, and long trends scroll horizontally with the latest results initially visible.

Transaction details open in a full-height sheet on the right from Activity, reports, account ledgers, unpaid items and Overview. The sheet uses the full screen on mobile, keeps its header visible while the body scrolls, supports Escape and its close button, and restores focus to the entry that opened it. Posted entries retain reversal-only correction; draft editing remains in the same sheet.

In **Reports → Movement**, choose a From and Through date to reconcile each balance-sheet account and the asset/liability/equity totals: opening immediately before From, signed movement during the inclusive period, and closing through Through. Accumulated unclosed results appear once within total equity. Closing journals can transfer value between accumulated results and equity accounts without changing total equity. Select any amount to open its supporting Activity account/group: opening and closing use cumulative As-of detail, while **Balance sheet movement** shows only period postings. Reports dates and presentation are preserved when returning.

In **Reports → Scenarios**, create a named experiment in a right-side sheet. Copy actual balances before the start date or enter a custom balanced opening position at account level. Positive assets use debit signs; positive liabilities/equity use credit signs, and negative balances are supported. Fixed-currency accounts retain native amounts and home carrying values separately; home-currency native and book balances must match. Previous revenue and expense balances become opening accumulated results once, so scenario P&L starts at zero. Select whole posted entries within the inclusive scenario period; drafts are excluded and reversals remain explicit.

Saving a scenario atomically freezes its source snapshot, dates, opening configuration and entry selection in owner-scoped storage. Reopening uses this frozen source, even if later actual entries or account names change. Saved experiments are immutable; create another scenario for a different setup, or delete an old one. The results show scenario P&L, opening/movement/closing amounts and read-only frozen journal detail. Scenarios never post to or modify the actual ledger. Historical replay keeps original journal amounts and does not recalculate FX carrying values, interest, operating decisions or payment feasibility. It is not a forecast or an unpaid-item reconciliation. Limits are 100 saved scenarios per workspace, 2,000 opening accounts/selected replay entries, a 200 KB request and an 8 MB frozen source snapshot; oversized inputs fail explicitly.

Apply migration `202610260001_financial_scenarios.sql` before using saved scenarios in an existing environment. It adds a separate scenario table and owner-checked commands without changing actual journal tables or past migrations.

For journals needing independent currencies or rates, choose **Add entry → Manual journal entry**. Add 2–100 debit/credit lines with original amounts; fixed-currency accounts retain their currency, while general accounts accepting any currency allow selection. Home values and totals are calculated automatically. Foreign asset/liability reductions use historical carrying values; add any FX gain/loss as an explicit line. Valid unbalanced drafts can be saved and reopened in the editor, but posting requires a zero home-currency difference and passes the existing database checks. Posted journals are corrected through reversals. Customer/supplier control accounts use the linked invoice, bill and payment forms. General payroll liability accounts can be used for manual salary accrual/settlement journals, without creating unpaid-item records or adding a payroll processing workflow.

## Shared accounting and application extensions

Guided/manual/payment forms now submit intent to the authenticated `commands` endpoint; the server rebuilds it against the authorized ledger snapshot and the database enforces final posting integrity. Invoice/bill and backend payroll adapters use shared obligation/settlement services above the same ledger. Legacy event/reversal APIs remain compatible. [ACCOUNTING_EXTENSIONS.md](ACCOUNTING_EXTENSIONS.md) documents the three layers, source-operation idempotency, atomic module/ledger writes, and a runnable backend payroll example. Payroll employee/run UI and statutory processing remain deferred.

The DB/API runners include all `.test.mjs` suites serially. The extension database suite first loads the pre-extension schema, seeds posted records, applies the additive migration, and compares historical snapshots. New unit and real-Auth API suites cover the payroll adapter and shared-source command boundary. Test data stays in the disposable local stack.
